## 決定した外部バックアップ保持方針

2026-09-25、ユーザー指定により**外部の暗号化DBバックアップは30日保持**と決定。

削除履歴の`deletions/`、期待一覧の`deletion-inventories/`、合成試験の`deletion-probes/`、復号鍵、Mac/USB内コピーはこの決定の対象外。
2026-09-26に自動削除設定の反映と初回実行を確認。期限超過候補がなく、実データの削除件数は0件。

`deploy/backup_retention_plan.py`に、認証済み一覧の保存結果から削除候補を計算する非破壊ツールを追加。

- バケットとprefixを固定し、不明なファイル名、重複、不完全/古い一覧、未来時刻は停止。

- 出力は常に`DeleteAuthorized=false`、`ObjectsDeleted=0`。削除コマンドやネットワーク処理は含まない。
- `Complete=true`は入力契約であり完全性の証拠ではない。実APIの全ページ取得記録と照合して使う。

### 承認済み期限切れ処理（反映・初回確認済み）

- `expire_backups.py`は毎時40分台に実行。固定bucketの既定形式のdb/だけを扱い、30×24時間を厳密に超えた世代を対象とする。
- uploaderと同じlockを取り、NTP同期・バックアップtimer/直前実行成功・2時間以内の検証済み世代を確認。
- versioning未使用、完全な一覧、最新世代のHEADを確認。削除候補があれば最新世代の暗号文もGET/hash照合する。
- 各対象をHEADで再確認し、削除意図をfsyncしてから単体DELETE。HEADで不在を確認後に完了を記録。
- 1回100件上限、時間上限、不正な名前/サイズ/時刻・versioning変更・認証失敗で停止。別キーへの切替やDELETE再試行なし。
- 既存の認証情報を通常利用する。鍵の取得/再保存、DB変更、deletions/・deletion-probes/・Mac/USBの削除は行わない。
- `If-Match`を送るが、さくらで条件付きDELETEが原子的に保証されるとは扱わない。既存uploaderはUUID名を再利用しない。
  同じdb/オブジェクトの手動上書きやversioning変更を並行実施しない。HEADとDELETEの間の外部管理者操作は共通lockでは防げない。
- 成功記録が2時間超古い、サービス失敗、timer停止なら既存healthを異常にする。実メール配送の再試験とは区別する。
- `バックアップ30日保持の有効化.command`で固定SHAのコードのみ反映し、初回処理と後続の自動health更新を確認する。
  失敗時は新timerを停止して旧healthを復元し、監査・設定ファイルを保持する。削除済み世代はロールバックしない。
- VPS上の有効な定期設定であり、Macの起動は不要。30日経過と同時の消去を保証しない。異常停止が起きた場合は原因を解消するまで保存が延びる。

さくらの[公式FAQ](https://manual.sakura.ad.jp/cloud/objectstorage/faq.html)では、管理画面の一覧は最新100件、
バージョニング利用時には画面に見えない旧世代が残る場合があると説明されている。
このため画面表示だけで全件/全世代の消去完了を判定しない。S3 APIは全操作の互換性保証ではなく、
今回読んだ公式案内からlifecycle設定の適用可否を断定していない。

## 現在の保持動作

| 対象 | 実装上の動作 | 公開前の未確定事項 |
|---|---|---|
| 稼働DBのゲームデータ | 削除処理は対象player/保存/操作/購入等を同一トランザクションで論理削除。現在は公開API無効 | iPhoneと実Appleを含む確認 |
| VPS内バックアップ | 成功したbackupコマンドで直近48世代＋過去30日の各UTC日最終世代を残す | 30日を超えても直近48世代は残り得る。厳密な30日以内消去ではない |
| 外部の暗号化DBバックアップ | 毎時PUT/GET照合。別timerで30日超のdb/世代を削除。異常時は停止 | 初回候補0件・削除0件。後続定期実行正常を確認。将来の実期限切れDELETEは未観測 |
| 削除履歴・再付与防止ハッシュ | outbox/外部deletions/等を期限だけで自動削除しない | 必要な保持目的・期間・容量・最新集合の完全性管理 |
| 削除結果照会proof | 外部確認待ちは保全、確認後は最低24時間延長。期限切れ行は次回previewで掃除 | 定期掃除ではないので「24時間で必ず消える」と説明しない |
| Apple暗号化grant | 失効処理成功で対象行を除去。未解決交換/世代記録を保全 | 実ワーカー・通知・運営解消手順・期限 |
| Mac/USB/手動退避/調査コピー | 自動期限切れ処理の対象外 | 保存先台帳と個別の安全な廃棄手順。鍵とバックアップは別物 |

注意: ハッシュ化は匿名化の保証ではない。論理削除はSSD/WAL/クラウド世代/旧バックアップの物理消去ではない。
削除イベントを先に消すと、残った旧バックアップから削除データが復活し得る。
DBバックアップと同じ一律lifecycleをdeletions/へ適用しない。
再付与防止ハッシュを消すと過去の購入が再利用され得るため、単なるバックアップ保存日数と連動させない。

## 障害発生時の順序

1. 公開ルートを閉じたままにし、実行中の書込みとワーカー状態を記録する。障害調査で本番DBを上書きしない。
2. 調査対象DB/WAL、instance ID、バックアップmanifest、外部履歴の確認記録を保全する。秘密鍵やtokenをログへ出さない。
3. 復元候補の出所・SHA-256・SQLite整合性・instanceを検査する。鍵は保管場所から通常の認証で利用する。
4. 復元したい時点ではなく、停止時点までの削除履歴を揃える。全ページ取得したbucket一覧だけを完全性の証拠にしない。
5. **事前に独立保管した最新の期待イベント一覧とそのhashが必要。** 一覧にはinstance、作成日時、event ID、平文SHA-256とサイズを持たせる。
   期待一覧をダウンロードしたイベントや古い復元DBから後付けで作ってはいけない。
   稼働DBを確認できる場合は書込み停止後のoutboxとの全件照合が必要。送信未完了は完了と見なさない。
   稼働DBを失い、独立した最新一覧もない場合、今回のツールは完全性を証明できない。公開せず復旧判断を止める。
6. 回収した暗号文をprivateな作業領域で復号し、`<event-id>.json`だけをprivateなeventsディレクトリに置く。
7. 下記オフラインツールで期待集合との完全一致を検証する。不足/余分/改変/instance不一致/不正時刻/公開権限は停止。
8. `deletion_restore.py restore-filtered`で**存在しない新規ディレクトリ**へ隔離復元し、削除済みデータを除外する。
9. 削除対象の不在、他プレイヤー保全、購入再付与防止、バックアップ後の取引/操作、Appleの現行所有者/失効状態を照合する。
10. `RECOVERY-PENDING.txt`は残す。この文書や成功レポートだけで解除しない。公開・instance再設定は別の検証付き復旧手順が必要。

## 削除履歴の期待一覧（実装・試験済み、空baselineで本番反映済み）

`deletion_inventory.py`を追加。実行元は稼働DBの所有者で、mode=ro/query_onlyの単一コミット済み読取りsnapshotを使用。
復元候補、instance不一致、未知schema、公開権限、symlinkを拒否し、DBの初期化・変更をしない。
outbox全件とdeleted_players/retired_purchasesの集合を照合し、一部の記録が欠けた場合は一覧を書き出さない。
送信済みだけでなくpending/sendingも期待集合に含める。未送信イベントを「なくてもよい履歴」と扱わない。
出力はevent ID・平文SHA-256・サイズのみ。player/取引ハッシュ、token、proof、イベント本文は含めない。
一覧もprivateファイルとして扱う。

以前の独立保管一覧と期待hashを渡して、イベントの消失・置換・作成時刻の巻き戻りを拒否する。
新規開始は明示的な`--bootstrap-empty`のみ許可し、履歴が1件でもあれば拒否する。
既存の非空履歴を任意のbaselineとして追認する機能はない。
出力先は存在しない新規ファイルに限定し、既存の証跡を上書きしない。

今回の終了条件（達成）:

- 空のbaselineからpending/sending/verifiedを含む一覧が増えることを合成DBで確認。
- outbox欠落、削除済みplayer記録欠落、購入再付与防止記録欠落/混入、全履歴の巻き戻りを拒否。
- 生成一覧を既存の`checkpoint_from_events`へ入力し、不足イベントがあれば復元用情報を生成しないことを確認。
- データベース行が不変であること、出力600・上書き禁止・復元候補拒否を確認。

外部保管の接続で守る条件（1〜3の稼働時照合は下記の専用workerで反映済み。DB喪失後の最新性確認は未完了）:

1. 同一snapshotから得た期待一覧を暗号化してDBバックアップとは別に保存し、読み戻し照合する。
2. イベントの保存だけで削除完了を返さず、当該イベントを含む一覧の保管確認も完了条件に加える。
3. 以前の一覧hash/世代の独立した記録を維持し、欠落したファイルや古いheadを最新と誤認しない。
4. 書込み停止後の最終一覧・未送信分を確認し、DB喪失時に最新性を確認できなければ復元候補を公開しない。

このCLIの`ExternallyStored=false`、`LatestCompletenessProven=false`は正しい表示。
一覧作成中にも新しい削除がコミットされ得るため、このsnapshotを作っただけで停止時点までの完全性を宣言しない。
以前の一覧とそのhashを同じ未確認の取得結果から作れば巻き戻り対策にならない。
一覧生成CLIのみの段階では本番を変更していない。その後、下記の専用workerを認証付きで反映した。

### 外部一覧とACK連動の追加実装（空baselineで反映・自動実行確認済み）

上記の一覧生成に続き、`deletion_inventory_ledger.py`と専用worker入口を追加。全390テスト成功。
通常workerの既存lock下で、DB所有者として一覧を読み、root側で既存の公開recipientを使って暗号化する。
秘密復号鍵はVPSへ送らず、既存のroot専用curl設定を通常利用する。資格情報の再取得・コピーはしない。

- `deletion-inventories/<instance>/`に世代別の暗号文と独立したheadを保存。どちらもprivate。
- 送信前にpending暗号文・世代をfsyncし、PUT後のGETをバイト単位照合。応答喪失時は同じ暗号文で再開。
- 一覧headの確認前には当該削除の完了ACKを返さない。イベント単体の転送成功だけでは不足。
- 前回のlocal receiptとcloud headを照合し、不在・不正・巻き戻りでは上書きせず停止。初期化は明示的な空履歴のみ。
- 一覧512KiB、累積送信予約64MiBの試験運用上限。予算は失敗した送信も消費し、再起動ではリセットしない。
  上限到達は異常停止・既存監視の対象。一般公開前の容量設計・承認された保全方針の代わりにはならない。
- 専用.commandは既存workerと権限制限を保存して切替。外部保存・後続自動実行・healthを確認する。
  失敗時は旧workerへ戻し、新しいstate/cloud証跡は保全。DB schemaや実アカウントは変更しない。

### 公開済み一覧から復旧資料を照合する手順

`deletion_recovery_evidence.py`は、独立保管したheadのSHA-256を入口に、取得head、暗号文、
復号済み期待一覧、全削除イベントを順に照合して新規checkpointだけを生成する。
世代/instance/オブジェクト名/サイズ/日時/件数の矛盾、入力改変、欠落・余分なイベントを拒否。
通信・復号・DB変更・復元候補の公開は行わない。入力所有者/600、ディレクトリ700、symlink拒否も既存CLIと同じ。
以下は説明用パス。秘密鍵はこのコマンドに渡さず、通常の認証付き復号手順で準備する。

```sh
python deletion_recovery_evidence.py \
  --head /secure/recovery/head.json \
  --expected-head-sha256 INDEPENDENTLY_RETAINED_REVIEWED_HEAD_SHA256 \
  --instance-id reviewed-instance \
  --ciphertext /secure/recovery/inventory.age \
  --inventory /secure/recovery/inventory.json \
  --events-dir /secure/recovery/decrypted-events \
  --output /secure/recovery/new-checkpoint.json
```

期待head hashを、その場でダウンロードしたheadから計算して入力しない。
生成されたcheckpointのSha256を既存の隔離復元へ渡す。`QuarantineMustRemain=true`を維持する。
8件の追加試験と既存の実age暗号化・復号試験で接続確認。本番への追加反映や認証操作は不要。

| 障害時に確保できた証拠 | 運用上の判断 |
|---|---|
| 稼働DBが残り、書込み停止後の全outboxと外部一覧/イベントが一致 | 削除集合を照合できる。隔離復元後、購入・Apple等の別確認へ進む |
| DBが失われ、外部headと過去のreceiptだけが残る | 一致する世代の資料検証まで。未送信の削除を否定できず、公開しない |
| head/暗号文/イベント欠落、世代不一致、最新性の証拠なし | 不足を空集合として扱わず停止。保全した証跡で運営判断する |

この区別により、不明な状態を「復旧完了」にしない。DB喪失後も自動で最新集合を証明する仕組みを実装したとは扱わない。
本番稼働後の復旧には、証跡保全・障害中の書込み停止・所有者確認を含む有人手順が残る。
