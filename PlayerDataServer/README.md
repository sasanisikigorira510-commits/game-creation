# プレイヤーデータ管理

通常の探索・育成・装備操作は端末で保存し、ガチャ、デイリー／ミッション／チュートリアル完了報酬、課金、有償石の永続強化はサーバーで取引を確定します。端末のセーブをアップロードしても、サーバーの石残高は変更されません。

ローカル検証に加え、単一VPS向けのGunicorn・HTTPSプロキシ・管理者別権限・整合バックアップ設定を追加しました。配置方法、予算、未接続の項目は [DEPLOYMENT.md](DEPLOYMENT.md) を参照してください。まだ外部公開・実課金接続はしていません。

## 起動

Python 3.9以降を使用します。ガチャ・管理画面・バックアップのローカル検証には追加パッケージは不要です。

```sh
cd /Users/andou/Desktop/game-creation
python3 PlayerDataServer/server.py
```

- 管理画面: `http://127.0.0.1:8787/`
- 管理トークン: `PlayerDataServer/.data/admin-token`（初回に自動作成。ブラウザーのパスワード欄へ入力）
- データベース: `PlayerDataServer/.data/players.sqlite`
- Unity Editor: 接続先が空の場合、上記ローカルサーバーへ接続します。
- 実機: `Assets/Resources/PlayerDataService.json` の `BaseUrl` にHTTPSの接続先を設定します。空の場合、オンライン取引は利用できません。HTTPはEditorのループバック接続だけ許可しています。

この起動方法は127.0.0.1だけで待ち受けるローカル検証用です。本番では別の `production:application_factory()` をGunicornから起動し、HTTPSと管理者個別の認証・権限を使います。設定不足や保存先の消失を検出した場合は停止します。監視通知・外部バックアップの接続は配置先の確定後に行います。管理トークンをアプリに入れないでください。

## 保存と再送

- `save.json.history/00000000000000000001.json` のような世代ファイルを、flush後のrenameで確定します。最新の世代ファイルが正本で、`save.json` と `.bak` は互換キャッシュです。
- 各世代にはPlayerId、SaveRevision、EconomyRevision、RecoveryEpoch、UTC保存日時、アプリ版、保存理由、異常の記録を含みます。直近100世代と直近30日の日別の最終世代を保持します。
- 旧形式のセーブは初回移行前のバイト列も `legacy-original.json` に保存します。
- 最新世代が読めない場合、古い課金状態へ勝手に戻したり、新規セーブで上書きしたりしません。復旧待ち画面で停止します。破損元は保持します。
- 端末の `online-identity.json` はインストールごとの認証情報です。再インストールや端末変更のためのApple等のログイン連携はまだありません。このファイルとセーブを別途保全してください。ローカルPlayerIdだけでは認証できません。
- オンライン要求は送信前に `online-request.json` へ保存し、要求IDで再送を重複排除します。サーバーは残高更新・取引結果・監査履歴を1つのDBトランザクションで確定します。
- サーバー確定後に通信や端末保存が失敗しても、次回同期で未反映の取引を順番に再適用します。端末は保存成功後にだけゲームへ結果を公開します。
- ホーム／ガチャ画面では約60秒ごとに同期します。通信時は画面への入力を遮断します。探索中は自動同期によるプロフィール差し替えを避けます。

## 既存ユーザーの初回移行

既に召喚・課金・石残高変更・チュートリアル完了のあるセーブは「移行確認待ち」にします。端末の残高を無条件には信用しません。

1. Unityを起動し、ホームでローカルサーバーへ接続します。通常プレイは継続できます。
2. 管理画面で該当のPlayerIdを選択し、保存履歴と購入記録などを照合します。
3. 操作者・理由・確認済みの無償石／有償石残高を入力して「初回移行を承認」を実行します。
4. 次回同期で、履歴付きの移行取引が端末に反映されます。既に受け取り済みの報酬・永続強化も移行時に記録します。

新規アカウントはサーバーが無償石900／有償石0から開始します。最初の3回の無償召喚は既存仕様のドラゴン→ゴーレム→魔法使い、IV50です。

## 異常の調査

現在の検出対象は負の通貨・不正な形式、端末とサーバーの石残高不一致、個体IDの欠落／重複などです。端末が報告した進行状態は `client_unverified` として保存します。検出だけでBANはしません。

オフライン戦闘の達成状況は端末からの申告です。報酬額、受取回数、受取日（日本時間）、残高更新はサーバーが管理しますが、改造端末が申告した戦闘勝利を完全には証明できません。重要な競争要素を追加する際は、戦闘結果のサーバー検証やオンライン限定ルールを追加してください。端末の暗号化やハッシュだけでは、この信頼境界は解消できません。

## 個別復旧

1. 問い合わせ対象のIDでユーザーを特定し、操作者・理由を記入します。
2. 「オンライン取引を停止」を実行します（オフライン進行はその場では停止できません）。
3. 保存履歴の「差分を確認」で、復旧前後を確認します。
4. 「確認した差分で復旧を登録」を実行します。差分確認後にデータが変わっていれば拒否します。
5. 端末側に復旧待ち画面が出ます。「復旧データを反映してホームへ」で、反映直前のローカル状態も履歴へ保存してから復旧します。
6. 再同期と結果確認後にオンライン取引を再開します。

復旧ではRecoveryEpochを増やし、古い端末状態からのアップロード・取引を拒否します。課金・ガチャ・報酬などの取引をまたぐ巻き戻しは拒否します。課金台帳を巻き戻して購入を消したり二重付与したりしないためです。この場合は、取引履歴を見て「通貨補正」で必要な増減を記録します。複数の購入や配合をまたぐアイテムの再計算・部分復旧は未実装です。

最新の端末世代そのものが破損した場合のクラウドからの起動時自動復旧は未実装です。現在は既存ファイルを保全してサポート対応する設計です。

## Apple課金検証

未設定時は `PurchasesEnabled=false` で、StoreKitの新規購入画面を開きません。保留中の購入も、検証・端末保存が完了するまで確認済みにしません。失敗時に未検証のローカル付与へ切り替える処理はありません。

```sh
python3 -m venv PlayerDataServer/.venv
PlayerDataServer/.venv/bin/pip install -r PlayerDataServer/requirements-apple.txt
```

次の環境変数を**サーバー側だけ**に設定して起動します。

- `WITCH_APPLE_BUNDLE_ID`: アプリのbundle ID
- `WITCH_APPLE_ENVIRONMENT`: 検証環境は `Sandbox`、本番は `Production`
- `WITCH_APPLE_APP_ID`: 本番の数値App ID
- `WITCH_APPLE_ROOTS_DIR`: Apple公式のルート証明書（`.cer`）を置いたフォルダ
- `WITCH_APPLE_KEY_FILE`: App Store ConnectのIn-App Purchaseキー（`.p8`）
- `WITCH_APPLE_KEY_ID` / `WITCH_APPLE_ISSUER_ID`

公式ライブラリでJWSの署名・証明書・環境・bundleを検証し、App Store Server APIから最新の取引を取得して、商品ID・数量・取消状態・appAccountTokenを照合します。購入開始時のappAccountTokenにはPlayerIdをUUID形式で設定します。取引IDはストア全体で一意に保存します。旧購入でappAccountTokenのないものは手動確認が必要です。

この作業では実際のキー・ストア・本番アカウントには接続していません。Apple Sandboxでの実購入、返金／取消通知の取り込みと継続的な照合、Google Playの購入検証はリリース前に追加検証・実装が必要です。

参考: [Apple公式ライブラリ](https://github.com/apple/app-store-server-library-python)、[Unityのレシート検証](https://docs.unity.com/en-us/iap/receipt-validation)

## DBバックアップ

```sh
python3 PlayerDataServer/server.py --backup /absolute/path/players-backup.sqlite
```

出力先は未作成のファイルを指定します。既存DBやバックアップには上書きしません。本番の世代管理・整合性検査・調査用コピー作成には `maintenance.py` を使用します。詳細は [配置・復旧手順](DEPLOYMENT.md) を参照してください。

SQLiteのbackup APIを使い、WALにある確定済みデータも含めてコピーします。稼働中の `.sqlite` ファイルだけの単純コピーは避けてください。検証用DBとは別の保存先へ世代管理し、復元テストを行います。サーバーの保存履歴・課金台帳・監査履歴は自動削除しません。運用開始前に保持期間と容量監視を決めてください。

## 検証

```sh
python3 -m unittest discover -s PlayerDataServer/tests -v
python3 PlayerDataServer/export_catalog.py
```

カタログはUnityのMasterDataRootが参照するモンスターから出力します。マスター変更時に再出力してください。Unityの `PlayerDataManagementTests` と `OnlinePlayerDataIntegrationTests` は破損保全、世代保存、取引の再適用、実HTTP接続、再送、再起動、通信断を検証します。既存のガチャ・ショップの画面テストはEditor限定の応答fixtureを使い、実サーバーの検証とは分けています。
